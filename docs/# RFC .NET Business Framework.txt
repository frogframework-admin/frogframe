# RFC: .NET Business Framework Berbasis Metadata --- Mendekati Frappe Framework

**Status:** Draft v2\
**Basis:** RFC Metadata-Driven Form Engine untuk Blazor\
**Arah teknologi:** C#, ASP.NET Core, Blazor, EF Core, PostgreSQL/SQL
Server\
**Tujuan:** Membangun framework aplikasi bisnis metadata-driven yang
terinspirasi oleh konsep Frappe Framework, tanpa mengharuskan framework
menjadi klon internal Frappe atau menyalin implementasinya.

## 1. Ringkasan

RFC awal berfokus pada form engine. Agar mendekati kapabilitas Frappe,
cakupan perlu diperluas dari:

`DocType → Form`

menjadi:

`DocType → Data Model → Form → List View → API → Permission → Workflow → Events → Reports`

Satu definisi DocType menjadi sumber utama untuk metadata field, layout,
validasi, relasi, permission, list view, filter, dan kontrak API. Namun,
metadata tidak boleh menjadi pengganti semua kode. Aturan bisnis yang
kompleks tetap dapat ditulis sebagai handler C# terdaftar melalui
interface yang stabil.

### Sasaran produk

Pengembang dapat mendefinisikan DocType dan workflow, lalu framework
menyediakan form, daftar data, CRUD/API, validasi, permission, audit,
notifikasi, dan pekerjaan latar belakang secara konsisten. Modul domain
tetap dapat menambahkan logika khusus dengan C#.

### Non-goals awal

-   Tidak menyalin implementasi internal atau source code Frappe.
-   Tidak membangun ERP lengkap sekaligus.
-   Tidak menjalankan kode arbitrer yang tersimpan dalam metadata.
-   Tidak menjanjikan kompatibilitas penuh dengan format DocType Frappe.
-   Tidak membuat schema database secara otomatis pada setiap perubahan
    metadata tanpa proses migrasi dan persetujuan.

## 2. Prinsip arsitektur

1.  **Metadata sebagai kontrak, bukan seluruh aplikasi.** Metadata
    mendeskripsikan struktur, UI, validasi deklaratif, permission, dan
    workflow. Aturan domain kompleks tetap berada dalam kode C#.
2.  **Server adalah otoritas.** Validasi, permission, filter data, dan
    transisi workflow selalu diperiksa di server.
3.  **Metadata berversi dan dapat dipublikasikan.** Draft tidak langsung
    memengaruhi pengguna produksi.
4.  **Core tidak bergantung pada Blazor atau komponen UI.** Renderer
    dapat diganti tanpa mengubah domain metadata.
5.  **Extension point eksplisit.** Custom field type, validator,
    handler, data source, workflow action, dan report provider
    didaftarkan melalui DI.
6.  **Database bukan sekadar JSON.** Data transaksional penting perlu
    memiliki tipe, constraint, indeks, relasi, dan strategi query yang
    jelas.
7.  **Tenant isolation sejak awal** jika produk ditujukan sebagai SaaS
    multi-tenant.
8.  **Tidak ada `eval`, Roslyn scripting, SQL dari metadata, atau
    refleksi bebas.** Ekspresi memakai parser dan fungsi allowlist.

## 5. Model metadata yang disarankan

Pertahankan konsep `DocTypeDef` dan `FieldDef` pada RFC awal, lalu
tambahkan metadata untuk persistence, lifecycle, API, list view, dan
workflow. Hindari satu class raksasa yang menampung semua kebutuhan;
pisahkan model berdasarkan tanggung jawab.

Contoh skema ilustratif:

``` json
{
  "name": "PurchaseRequest",
  "version": 1,
  "title": "Purchase Request",
  "storage": {
    "strategy": "relational",
    "table": "purchase_requests"
  },
  "document": {
    "trackChanges": true,
    "allowDraft": true,
    "allowSubmit": true,
    "allowCancel": true
  },
  "fields": [
    {
      "name": "requester",
      "type": "Link",
      "label": "Requester",
      "linkTo": "Employee",
      "requiredWhen": "true",
      "inListView": true
    },
    {
      "name": "request_date",
      "type": "Date",
      "label": "Request Date",
      "requiredWhen": "true",
      "default": "$today",
      "inListView": true
    },
    {
      "name": "total",
      "type": "Currency",
      "label": "Total",
      "readOnlyWhen": "true",
      "compute": "sum(items.amount)",
      "inListView": true
    },
    {
      "name": "items",
      "type": "Table",
      "label": "Items",
      "childDocType": "PurchaseRequestItem"
    }
  ],
  "listView": {
    "titleField": "requester",
    "defaultSort": [{ "field": "modified", "direction": "desc" }],
    "searchFields": ["name", "requester"],
    "filters": ["request_date", "status"]
  },
  "permissions": [
    {
      "role": "Requester",
      "actions": ["read", "create", "write"],
      "scope": "owner"
    },
    {
      "role": "Procurement",
      "actions": ["read", "write", "submit"],
      "scope": "all"
    }
  ]
}
```

Contoh di atas adalah format usulan, bukan format Frappe yang kompatibel
langsung. Sintaks ekspresi, default dinamis, field `modified`, dan
agregasi harus didefinisikan secara formal sebelum dipakai.

### Metadata tambahan

-   `DocumentDef`: naming, lifecycle, ownership, track changes,
    attachment.
-   `ListViewDef`: kolom, pencarian, filter, sorting, grouping.
-   `PermissionDef`: aksi dan row-level scope.
-   `WorkflowDef`: state, transition, action, kondisi, assignment.
-   `ApiDef`: operasi yang diizinkan, field yang diekspos, rate limit.
-   `ReportDef`: filter, kolom, grouping, sumber data.
-   `ModuleDef`: kumpulan DocType, workflow, report, menu, permission,
    dan dependency.

## 6. Document model dan lifecycle

Jangan menganggap setiap dokumen hanya sebagai JSON yang bebas diubah.
Definisikan kontrak lifecycle:

``` text
New
  └─ insert → Draft
Draft
  ├─ save → Draft
  ├─ submit → Submitted
  └─ delete → Deleted (jika kebijakan mengizinkan)
Submitted
  ├─ cancel → Cancelled
  └─ amend → dokumen baru yang merujuk dokumen asal
```

Status aktual dapat dikonfigurasi per DocType. Tidak semua dokumen perlu
submit/cancel.

Interface awal:

``` csharp
public interface IDocumentHandler
{
    Task BeforeValidateAsync(DocumentContext context, CancellationToken ct);
    Task ValidateAsync(DocumentContext context, CancellationToken ct);
    Task BeforeSaveAsync(DocumentContext context, CancellationToken ct);
    Task AfterSaveAsync(DocumentContext context, CancellationToken ct);
    Task BeforeSubmitAsync(DocumentContext context, CancellationToken ct);
    Task AfterSubmitAsync(DocumentContext context, CancellationToken ct);
    Task BeforeCancelAsync(DocumentContext context, CancellationToken ct);
    Task AfterCancelAsync(DocumentContext context, CancellationToken ct);
}
```

Catatan: untuk API publik yang stabil, lebih baik hook opsional
dipisahkan menjadi interface kecil atau base class dengan virtual
method. Jangan mewajibkan implementasi semua method jika tidak
diperlukan.

Urutan save harus eksplisit: load metadata aktif → authorize → load
dokumen dan cek concurrency → normalize payload → apply permitted fields
→ validate → execute handler → persist dalam transaksi → write
audit/outbox → commit. Event eksternal dipublikasikan setelah commit
melalui outbox, bukan sebelum transaksi selesai.

## 7. Strategi penyimpanan

Ada dua pilihan utama.

### A. Tabel generik + payload JSON

Setiap dokumen disimpan pada tabel umum dengan `doctype`, `name`,
`owner`, `status`, `created`, `modified`, `version`, dan `data JSONB`.

Kelebihan: metadata bisa berubah cepat dan tidak selalu perlu migrasi
tabel. Kekurangan: query relasional, constraint, indeks per field, join,
agregasi, dan laporan kompleks lebih sulit.

Cocok untuk: prototipe, konfigurasi, formulir yang jarang dipakai untuk
analitik berat.

### B. Tabel relasional per DocType

Metadata dipetakan ke kolom dan tabel relasional. Perubahan schema
dilakukan melalui migration plan yang dihasilkan, ditinjau, dan
dieksekusi secara terkontrol.

Kelebihan: query, constraint, indeks, join, dan integrasi laporan lebih
natural. Kekurangan: metadata publish dapat memerlukan migrasi database
dan koordinasi deployment.

Cocok untuk: ERP/HRIS produksi, payroll, keuangan, dan data yang
membutuhkan integritas kuat.

### Rekomendasi

Gunakan **hybrid secara sadar**, bukan satu strategi untuk semua data:

-   Metadata dan definisi fleksibel disimpan di tabel metadata dengan
    versi.
-   Dokumen operasional kritis menggunakan relational storage.
-   JSONB dipakai untuk field tambahan atau konfigurasi yang memang
    fleksibel.
-   Child table yang butuh perhitungan, relasi, dan pelaporan penting
    sebaiknya memiliki tabel relasional sendiri.
-   Schema migration selalu menghasilkan preview, backup/rollback plan,
    dan pemeriksaan kompatibilitas.
-   Gunakan EF Core untuk persistence terdefinisi dan Dapper bila query
    read/report membutuhkan kontrol SQL. Hindari mengandalkan EF Core
    untuk membuat semua struktur database secara dinamis tanpa batas.

## 8. Metadata compiler dan registry

Saat metadata dipublikasikan, jalankan pipeline:

1.  Deserialize dan validasi struktur.
2.  Validasi nama, tipe field, referensi DocType, field duplikat, dan
    layout.
3.  Parse ekspresi ke AST; tolak fungsi/operator yang tidak dikenal.
4.  Validasi dependensi dan deteksi siklus pada `fetchFrom`/`compute`.
5.  Validasi permission, Link target, child DocType, dan konfigurasi
    list view.
6.  Buat compiled metadata/cache dengan key `DocType + Version`.
7.  Buat migration plan jika strategi storage memerlukan perubahan
    schema.
8.  Simpan versi sebagai `Published` hanya setelah seluruh pemeriksaan
    dan persetujuan lolos.

Registry yang perlu tersedia melalui DI:

``` csharp
public interface IFieldTypeRegistry
{
    bool TryGet(string type, out IFieldType fieldType);
}

public interface IFieldType
{
    string Name { get; }
    Type ClrType { get; }
    bool IsValidValue(object? value);
    object? Normalize(object? value);
}

public interface IValidatorRegistry { /* resolve validator by stable name */ }
public interface ILinkDataSourceRegistry { /* resolve allowed link source */ }
public interface IDocumentHandlerRegistry { /* resolve handler by DocType */ }
```

Tanda tangan di atas bersifat konseptual; detail async, error model,
nullable value, localization, dan serialization perlu ditetapkan dalam
desain API.

## 9. Ekspresi dan compute

Gunakan parser terbatasi dengan AST. Operator yang diizinkan misalnya
`==`, `!=`, `>`, `>=`, `<`, `<=`, `&&`, `||`, `!`, `in`, aritmetika
dasar, dan fungsi allowlist seperti `empty`, `len`, `sum`.

Persyaratan keamanan: - Tidak boleh mengeksekusi C#, JavaScript, SQL,
atau kode arbitrer dari metadata. - Batasi panjang ekspresi, kedalaman
AST, jumlah operasi, dan waktu evaluasi. - Bedakan ekspresi UI
(visible/required/read-only) dari perhitungan bisnis otoritatif. -
Hitung ulang nilai turunan penting di server. - `compute` yang
memengaruhi harga, payroll, saldo, atau limit harus menggunakan aturan
domain yang dapat diuji dan tidak boleh dipercaya dari payload client. -
Versi bahasa ekspresi harus dicatat agar perubahan semantik tidak
mengubah metadata lama secara diam-diam.

## 10. Permission dan keamanan

Permission bukan hanya menyembunyikan tombol. Setiap operasi harus
memeriksa: - akses terhadap DocType dan aksi (`create`, `read`, `write`,
`delete`, `submit`, `cancel`, `export`); - akses ke dokumen tertentu
(row/document scope); - akses field berdasarkan role/permission level; -
akses ke field sensitif dan attachment; - hak menggunakan Link target
serta filter pencarian; - hak melihat report dan mengekspor data.

Prinsip implementasi: - Terapkan permission di application service/API,
bukan hanya renderer Blazor. - Field yang tidak boleh dibaca tidak
dikirim ke client. - Field yang tidak boleh ditulis dihapus dari patch
atau ditolak sesuai kebijakan; jangan menerima nilainya begitu saja. -
Terapkan tenant scope pada semua query, termasuk Link lookup, report,
export, background job, dan audit. - Tolak field tak dikenal atau field
yang tidak boleh diubah. - Audit akses untuk data sensitif sesuai
kebijakan. - Tambahkan test negatif untuk IDOR, mass assignment, tenant
escape, dan privilege escalation.

## 11. Workflow engine

Workflow adalah state machine, bukan sekadar status string pada form.

Model minimal:

``` text
WorkflowDefinition
  - DocType
  - States
  - InitialState
  - Transitions
      - FromState
      - ToState
      - Action
      - AllowedRoles
      - Condition
      - RequireComment
      - AssignmentRule
```

Mesin workflow harus memeriksa role, kondisi, status dokumen terkini,
dan concurrency di server. Transisi dijalankan dalam transaksi yang sama
dengan perubahan status. Setiap transisi mencatat actor, waktu, state
asal/tujuan, komentar, dan versi workflow.

Mulai dari approval linear dan branching sederhana. Delegasi, parallel
approval, escalation, SLA, dan visual workflow builder bisa menjadi fase
berikutnya.

## 12. Event, jobs, notification, dan scheduler

Sediakan: - Domain event internal setelah operasi dokumen. - Outbox
transactional untuk menjamin event tidak hilang setelah commit. -
Background job queue dengan retry, backoff, idempotency key, dead-letter
handling, dan observability. - Scheduler untuk pekerjaan periodik. -
Notification inbox dan adapter email; channel tambahan dapat menyusul.

Jangan memulai dengan banyak infrastruktur terpisah jika kebutuhan belum
jelas. Untuk fase awal, gunakan implementasi queue sederhana yang dapat
diganti, lalu integrasikan PostgreSQL/SQL Server outbox dan worker.
RabbitMQ atau broker lain dapat ditambahkan jika skala dan kebutuhan
distribusi membenarkannya.

## 13. List view, filter, API, dan report

### List view

Gunakan metadata `inListView`, tipe field, label, format, default sort,
dan filter. Backend wajib membuat query dari daftar field/operator yang
diizinkan; jangan menyusun SQL dari string filter client.

Minimum: - server-side pagination; - sorting dan filtering allowlist; -
quick search pada field yang disetujui; - saved views; - bulk action
dengan permission per dokumen; - export yang menerapkan filter dan
permission yang sama.

### Generic API

Rute konseptual:

``` text
GET    /api/data/{doctype}
GET    /api/data/{doctype}/{name}
POST   /api/data/{doctype}
PATCH  /api/data/{doctype}/{name}
DELETE /api/data/{doctype}/{name}
POST   /api/data/{doctype}/{name}/actions/{action}
GET    /api/meta/{doctype}
GET    /api/meta/{doctype}/versions/{version}
GET    /api/links/{target}
```

Jangan mengekspos semua operasi secara otomatis tanpa opt-in.
Definisikan API policy per DocType, DTO publik, pagination, idempotency
untuk operasi tertentu, rate limit, audit, dan error response yang
konsisten.

### Report

Mulai dari report provider C# yang terdaftar, dengan filter dan kolom
terdefinisi. Jangan menjalankan SQL bebas dari metadata. Fase berikutnya
dapat menyediakan query builder terbatas, grouping, agregasi, export
XLSX/CSV/PDF, dan permission report.

## 14. Multi-tenancy dan identitas

Jika targetnya SaaS: - Tentukan sejak awal model tenant: database per
tenant, schema per tenant, atau shared database dengan `TenantId`. -
Untuk shared database, semua unique key, indeks, query, cache key, job,
file, dan audit harus mempertimbangkan tenant. - Tenant context berasal
dari identitas/token yang tervalidasi, bukan dari payload client. - Uji
bahwa pengguna tenant A tidak dapat membaca, menulis, mencari, atau
mengekspor data tenant B. - Gunakan OIDC/OAuth2 untuk autentikasi dan
mapping role/permission yang jelas.

Jangan menunda desain tenant sampai aplikasi sudah memiliki banyak data.

## 15. Versioning, publish, upgrade, dan rollback

Siklus metadata:

`Draft → Validated → In Review → Published → Deprecated`

Setiap publish menyimpan versi immutable. Dokumen dapat mencatat
`DocType`, `SchemaVersion`, dan `WorkflowVersion` yang dipakai saat
dibuat atau diproses.

Perubahan metadata harus diklasifikasikan: - **Aman:** perubahan label,
deskripsi, urutan tampilan. - **Perlu transformasi:** rename field,
perubahan tipe, perubahan default. - **Berisiko:** penghapusan field
berisi data, perubahan key, perubahan relasi, perubahan constraint.

Sediakan diff metadata, migration preview, backup/rollback plan,
compatibility check, dan maker-checker untuk produksi. Rollback metadata
tidak selalu berarti rollback data; transformasi data harus memiliki
strategi tersendiri.

## 16. Pengujian dan observability

Wajib tersedia: - unit test parser/AST dan validasi; - metadata contract
test; - integration test CRUD dan transaksi; - permission test untuk
setiap aksi; - tenant isolation test; - concurrency test; - workflow
transition test; - test untuk payload manipulatif; - test migration dan
rollback; - log terstruktur dengan correlation ID; - metrik untuk
validasi gagal, permission denied, job retry, workflow, dan waktu
query; - audit log dipisahkan dari log diagnostik biasa.

Jangan mencatat token, credential, atau nilai PII lengkap dalam log.

## 17. Roadmap yang disarankan

### Fase 0 --- Keputusan fondasi

Tetapkan target penggunaan pertama, database, tenant model, identitas,
storage strategy, versi .NET, aturan metadata, dan kebijakan dependency.
Buat threat model dan keputusan arsitektur ringkas.

**Kriteria selesai:** keputusan arsitektur terdokumentasi dan satu
DocType pilot disepakati.

### Fase 1 --- Metadata & Form

DocType/Field registry, JSON serializer, metadata validation, renderer,
tab/section/column, 10--15 field type prioritas, expression engine
dasar, dan validation engine bersama.

**Kriteria selesai:** form pilot dapat dirender dari metadata, diuji,
dan dipublikasikan sebagai versi.

### Fase 2 --- Persistence & CRUD

Document service, repository, transaksi, concurrency, naming,
create/read/update/delete, lifecycle dasar, audit perubahan, dan API
generik yang dibatasi permission.

**Kriteria selesai:** dokumen dapat dikelola melalui UI dan API dengan
validasi server.

### Fase 3 --- List, Link, child table & permission

List view, filter/sort/paging, Link lookup, FetchFrom, child table,
DocType/field/row permission, dan tenant isolation jika multi-tenant.

**Kriteria selesai:** satu proses bisnis end-to-end dapat dipakai
beberapa role dengan data scope berbeda.

### Fase 4 --- Workflow & events

Submit/cancel, workflow state machine, handler hooks, outbox, background
worker, scheduler, dan notifikasi.

**Kriteria selesai:** proses pengajuan dan approval memiliki audit trail
dan tidak dapat melewati aturan melalui API langsung.

### Fase 5 --- Reports & data operations

Report provider, export, import dry-run, saved views, serta job untuk
operasi besar.

**Kriteria selesai:** laporan menerapkan permission dan tenant scope
yang sama dengan UI.

### Fase 6 --- Admin builder & packaging

Metadata editor, preview, diff, publish workflow, rollback metadata,
module/package dependency, dan developer documentation.

**Kriteria selesai:** tim dapat membuat atau mengubah DocType melalui
admin tool dengan proses review yang terkontrol.

## 18. Pilot yang disarankan

Pilih **Purchase Request / Pengajuan Pembelian** atau **Parameter
Produk** untuk pilot pertama, bukan payroll atau jurnal keuangan.

Purchase Request cukup kaya untuk menguji: - field dasar dan currency; -
Link ke Employee/Vendor; - child table item; - total terhitung; - list
view dan filter; - permission pemohon versus approver; - workflow Draft
→ Submitted → Approved/Rejected; - audit trail dan notification.

Setelah fondasi stabil, baru uji domain lebih kritis seperti HRIS atau
payroll dengan persyaratan audit, perhitungan, dan integritas data yang
lebih tinggi.

## 19. Keputusan yang masih perlu diambil

1.  Apakah targetnya framework internal untuk satu produk, atau
    framework reusable untuk banyak aplikasi?
2.  Apakah multi-tenancy wajib sejak versi pertama?
3.  Apakah PostgreSQL menjadi database utama, dengan SQL Server sebagai
    provider tambahan?
4.  Apakah dokumen operasional memakai tabel relasional per DocType,
    JSONB, atau hybrid?
5.  Apakah workflow awal cukup linear/branching atau membutuhkan
    parallel approval?
6.  Siapa yang boleh publish metadata dan menjalankan schema migration?
7.  Apakah API generik tersedia untuk semua DocType atau harus
    diaktifkan satu per satu?
8.  Apakah Blazor Server, WebAssembly, atau Auto menjadi target utama?
9.  Apa persyaratan internal untuk lisensi, SCA, security review, dan
    dependency approval?

## 20. Kesimpulan

Agar mendekati Frappe, jangan berhenti pada dynamic form. Bangun
platform metadata dengan enam fondasi: **DocType, document service,
permission, lifecycle/workflow, generic views/API, dan extension
system**. Report, scheduler, notification, import/export, dan builder
mengikuti setelah fondasi transaksi dan keamanan benar.

Kunci desainnya adalah metadata yang dapat divalidasi dan dipublikasikan
secara terkontrol, business logic C# yang tetap testable, dan
server-side authorization yang konsisten. Ini memberi pengalaman
developer yang mirip framework bisnis, tanpa mengorbankan kekuatan .NET
dan tanpa mencoba mengimplementasikan seluruh Frappe sekaligus.
